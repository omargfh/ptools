# Render OS requirements in the generator and retire the hand-edit guidance

**Goal**: Give `scripts/generate_requirements.py` an OS comment section, regenerate `full_requirements.txt`, and fix the `AGENTS.md` gotcha that currently tells agents to hand-edit that file.

**In scope**: OS rendering in `_format_output` (`scripts/generate_requirements.py:79-152`); a regenerated `full_requirements.txt`; the `full_requirements.txt` gotcha in `AGENTS.md:54` and the pointer at `AGENTS.md:47`.

**Out of scope**: the generator/committed-file drift unrelated to OS requirements — the two header-punctuation defects and the `tabulate` floor — which stay with `.ongoing/requirements-generator-drift/fix-generator-1.md`.

**Description**: After `add-os-requirement-type-1.md`, the generator no longer misfiles OS gates under "System binaries" (`generate_requirements.py:118-123`), but it drops them entirely, since `_format_output` filters by `isinstance` for the three known types (`generate_requirements.py:90-92`). Add an OS comment section alongside the existing binary and key sections so a reader of `full_requirements.txt` can still tell that some commands are macOS-only.

This PR also settles a documentation defect the type fix creates. `AGENTS.md:54` records the repeated `darwin` lines as unexplained generator drift and concludes: "Hand-edit `full_requirements.txt` rather than regenerating until the generator is fixed." That advice is what has been perpetuating the drift — hand-editing is how the committed file came to pin `tabulate>=0.8.0` (`full_requirements.txt:27`) while `pyproject.toml:22` pins `tabulate>=0.10.0`. Once the OS cause is fixed and the file is regenerated, the gotcha is actively false and must go.

Verified 2026-07-18, the OS fix accounts for exactly the `darwin` portion of the drift and nothing else. Suppressing the four `darwin` lines from today's generator output leaves precisely three differences against the committed file:

```
$ diff <(python scripts/generate_requirements.py | grep -v '^#   - darwin$') full_requirements.txt
1c1
< # Complete ptools requirements; generated by scripts/generate_requirements.py.
---
> # Complete ptools requirements - generated by scripts/generate_requirements.py.
5c5
< # This file is intentionally NOT referenced from pyproject.toml it exists
---
> # This file is intentionally NOT referenced from pyproject.toml - it exists
25d24
< tabulate>=0.10.0
27a27
> tabulate>=0.8.0
```

Those three are `fix-generator-1.md`'s remit, not this PR's. Note the second one is a real generator bug, not a stylistic difference: the implicit string concatenation at `generate_requirements.py:112-114` drops the separator and emits the ungrammatical "pyproject.toml it exists".

**Acceptance criteria**:
- Generator output contains an OS section listing the announced OS requirements, omitted entirely when there are none.
- Each distinct OS requirement appears exactly once. The registry announces `darwin` four times (`fs.py:343,354,387,423`) and the generator does not dedup (`generate_requirements.py:118-123`), so without either local dedup or `dedup-requirement-registry-4.md` this section reproduces the same four-duplicate-lines defect the task set out to remove.
- `full_requirements.txt` is regenerated and committed; it no longer contains a hand-edited `tabulate` floor that contradicts `pyproject.toml:22`.
- `AGENTS.md:54` no longer attributes the drift to an unknown cause and no longer instructs hand-editing; `AGENTS.md:47` agrees with it.
- `.ongoing/requirements-generator-drift/fix-generator-1.md` is updated: its acceptance criterion "No duplicate/placeholder OS binary entries (e.g. repeated `darwin`) appear in generator output" is satisfied here, and its description should no longer present the `darwin` lines as an open question.

**Depends on**: `add-os-requirement-type-1.md`

**Notes**: coordinate with `fix-generator-1.md` — whichever lands second must re-run the diff, since both change generator output. Landing `fix-generator-1.md` first is the cleaner order: it makes the byte-for-byte criterion achievable, and this PR then regenerates once against a correct generator. Also sequence against `dedup-requirement-registry-4.md`, which changes generator output again.
